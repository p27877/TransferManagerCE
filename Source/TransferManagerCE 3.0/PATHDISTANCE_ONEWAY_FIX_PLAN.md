# Path Distance One-Way Direction Fix

## Summary

This branch fixes one-way road handling in TransferManagerCE's path-distance based offer matching.

The goal is to make TMCE respect actual outbound road directions when evaluating path-distance candidates, instead of relying on a global search direction that can allow invalid travel across one-way segments.

## What Changed

### 1. Node link generation now respects outbound segment direction

`PathDistance/NodeLinkGenerator.cs` now builds only legal outbound links from the current node.

- Segment links are no longer added to both end nodes unconditionally
- The generator now checks whether the current node can legally travel toward the segment's start node or end node
- One-way segments only contribute links in the permitted direction
- Lane sub-nodes are filtered to the same outbound direction so lane-level connections do not reintroduce reverse travel

### 2. Path-distance search now trusts the generated graph

`PathDistance/PathDistance.cs` no longer applies a single global `Forward` or `Backward` filter while traversing links.

- Search now expands all links returned by the node-link graph
- Direction correctness is enforced during graph construction instead of during Dijkstra expansion
- This removes the mismatch between local road direction and the old global direction flag

### 3. Middle-node bypass now accepts one-way sink endpoints without changing general bypass semantics

`PathDistance/MiddleNodeBypass.cs` still follows the existing middle-node bypass pattern, but now also handles directed sink endpoints correctly.

- Ordinary `Count == 2` corridor nodes still qualify as pass-through nodes
- Directed `1-in / 1-out` nodes are now also treated as pass-through nodes so one-way corridors can be collapsed
- A visited-node set stops bypass traversal from recursing forever on loops
- Generated bypass links target the legal endpoint directly from the already-filtered outbound graph

### 4. Sink endpoints are normalized in the graph without changing connectivity semantics

`PathDistance/NodeLinkGraph.cs` now materializes referenced sink endpoints as empty graph entries so they can be treated as legal terminal nodes.

- Nodes that are only reached by incoming one-way links are added to the graph as empty `NodeLinkData()` entries
- `HasNodeLinks(node)` still only reports nodes with actual outbound links, so `PathConnected` keeps its existing weak-component behavior and does not seed sink nodes as standalone components
- This keeps sink endpoints available for bypass/path-distance traversal without changing Connected LOS or `PathConnectedCache` semantics

### 5. Test and debug path refresh now keeps connectivity in sync

`PathDistance/PathDistanceTest.cs` now refreshes `PathConnectedCache` alongside `PathDistanceCache`.

- Debug/test queries no longer risk using stale connectivity after a graph invalidation
- This aligns the test path with the production match-offer setup sequence

## Behavior

When TMCE performs path-distance matching:

1. Build a node-link graph for the requested network mode
2. For each node, add only links that represent legal outbound travel
3. Exclude one-way reverse travel from both segment links and lane sub-node links
4. Materialize referenced sink endpoints as empty graph nodes so they remain legal terminal nodes
5. Use the existing weak component coloring for coarse connectivity checks
6. Traverse the graph without applying a separate global direction filter
7. Select the nearest reachable candidate from the resulting legal graph

## Why This Fix Exists

The previous 3.0 path-distance graph could generate reverse links for one-way segments and then try to correct that later with a global search direction.

That model was not accurate enough for real road networks, because each segment's legal travel direction depends on the current node, the segment orientation, and the lane directions on that segment. As a result, path-distance matching could treat one-way roads as partially reversible and pick candidates that were not actually reachable by legal travel.

This branch fixes that by enforcing direction legality when the graph is built, which is the correct level for representing one-way restrictions.

## Limitations

- This branch improves TMCE's path-distance offer matching only
- Actual in-game vehicle routing after dispatch is still handled by the game's normal pathfinding systems
- Full build verification could not be completed in this workspace because the local environment is missing the game's managed assembly references (`Assembly-CSharp`, `ICities`, `UnityEngine`, etc.)
- Runtime validation in-game is still recommended for one-way, inverted, and lane-heavy road layouts

## Expected Result

TMCE should no longer traverse one-way roads in the forbidden direction during path-distance matching, and candidates that terminate at legal one-way sink nodes should no longer be filtered out before Dijkstra runs. In practice this should improve candidate selection around one-way streets, ramps, service roads, dead-end sink nodes, and other directional road layouts where the old global direction filter and sink-handling assumptions could produce invalid reachability.
